I spent last Saturday afternoon running the same prompt through three different quantizations of the same model and staring at `tok/s` numbers in a terminal. My M4 Pro has 48GB of unified memory, which sounds like a lot until you try to load a 70B model and realize you can fit it or you can run it fast, but not both.

Here is what I found.

Q4_K_M is the sweet spot. Not because it is theoretically optimal. Because it is the quantization where local inference stops feeling like a punishment.

I tested three checkpoints of Qwen2.5-14B: F16 (28GB on disk), Q8 (15GB), and Q4_K_M (8.2GB). All loaded in llama.cpp, Metal acceleration on, 4096 token context, single user, no server mode. The prompt was a 200-token coding question and I measured time to first token and sustained throughput.

<BarChart title="Qwen2.5-14B throughput, M4 Pro, 4096 ctx" unit="tok/s" data={[{ label: "F16", value: 22 }, { label: "Q8", value: 38 }, { label: "Q4_K_M", value: 61 }]} />

F16 at 22 tok/s is usable for a chat interface. It is not usable for agentic loops where the model calls itself five times in a row and you are sitting there waiting. Q8 at 38 tok/s is better. Q4_K_M at 61 tok/s is where the model stops being the bottleneck and your prompt engineering becomes the bottleneck.

The memory story matters more than the speed story. F16 for the 14B model eats 28GB. The 48GB machine can handle it, but barely. Add a browser, a Docker compose stack, and VS Code and you are swapping. Q4_K_M at 8.2GB leaves headroom for everything else. I can run the 14B model and still have 30GB free for actual work.

I also ran the same three quantizations on Qwen2.5-7B and Llama-3.3-70B to see if the pattern held. It did, with one twist.

For the 7B model, Q4_K_M hit 118 tok/s. That is fast enough that you stop thinking about tokens and start thinking about responses. Q8 gave 84 tok/s. F16 gave 52 tok/s. For a model this small, I actually prefer Q8. The speed difference between Q4 and Q8 is 34 tok/s, which you feel, but the 7B model is small enough that Q8 still fits comfortably in memory and the quality difference is more visible on coding tasks where the 7B is already at the edge of its competence.

The 70B model is where quantization stops being a preference and becomes a hard constraint. F16 does not fit. Q8 at 70GB does not fit. Q4_K_M at 39GB fits, and gives me 14 tok/s. That is slow. It is also the only way I can run a 70B model on this machine at all without renting a GPU. I have used it for difficult reasoning prompts where I care about the answer more than the latency, and 14 tok/s is tolerable when the alternative is not running the model.

The quality question is the one everyone asks and nobody wants to hear the answer to. My honest take after a few hundred prompts across these checkpoints: Q4_K_M is noticeably worse than F16 on math and on tasks that require precise token-level reasoning. On coding, writing, and general chat, I cannot reliably tell the difference in a blind test. I tried. I ran the same 20 prompts through Q4_K_M and F16 side by side, shuffled the outputs, and tried to guess which was which. I got 11 out of 20 right. That is barely above chance.

There is a specific failure mode I have seen with Q4_K_M that I have not seen with Q8. Long-context retrieval degrades. When I stuff 6000 tokens of context into the prompt and ask the model to find a specific detail, Q4_K_M misses it more often than Q8 does. I have not measured this rigorously. It is a pattern I noticed after debugging a retrieval prompt for a week and switching to Q8 fixed it. Take that as an anecdote, not a benchmark.

Here is my current setup. I keep Q4_K_M as the default for anything I run locally. For coding and writing, it is fine. For anything involving math, multi-step reasoning, or long-context retrieval, I switch to Q8 if the model fits in memory. F16 I almost never use locally. It exists for when I need the cleanest possible output and latency does not matter, which is rare.

The practical lesson is this. Quantization is not a dial where you trade quality for speed in a linear way. Q4_K_M is a cliff edge on one side and a flat plateau on the other. Below Q4, quality collapses. Above Q4, you pay a lot of memory and speed for very little quality. Q4_K_M is where you land when you have spent enough time staring at tok/s numbers to know that the theoretical best option and the practically best option are not the same thing.
